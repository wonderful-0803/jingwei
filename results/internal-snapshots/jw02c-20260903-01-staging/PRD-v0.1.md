## 1. 产品定位与版本目标

### 1.1 产品定位

Jingwei 是基础设施，不是文件助手、聊天产品或某个行业 Agent。它为 Rust 应用提供模型、工具、上下文、执行策略、资源预算和恢复机制的组合接口，并提供可替换的官方实现。

应用保有业务规则、模型选择、数据位置、权限和异步运行时的控制权。框架负责降低将小模型接入可控 Agent 系统的工程成本，不承诺补足模型本身不具备的推理能力。

“面向小模型”体现为可限制的决策范围、上下文和资源消耗，以及模型能力差异的显式表达；不得表现为把某个模型名称、参数规模、固定任务流程或设备型号写进核心接口。

### 1.2 v0.1 目标

使用者无需修改框架源码，即可：

1. 接入受支持的本地模型，以原生工具调用或受约束结构化输出表达动作。
2. 用有限上下文和有限预算运行官方参考 Agent，也可完全替换其策略。
3. 通过统一工具接口执行动作、接收反馈、修正错误或请求用户补充信息。
4. 查看执行证据，并从安全检查点恢复受支持的任务。
5. 按开发指南完成入门、定制、测试、故障排查及旧版本迁移。

### 1.3 用户与核心场景

| 使用者 | 需要完成的框架级工作 |
| --- | --- |
| 宿主应用开发者 | 配置模型、注册工具、设定权限和预算，嵌入 Agent；不需要自己重写标准工具循环 |
| 框架扩展开发者 | 实现模型适配器、上下文策略、动作策略、工具或状态存储；不修改其他模块 |
| 集成与测试人员 | 替换为假模型和假工具、复现执行轨迹、验证故障和资源边界 |

验收示例只用于证明这些能力可组合，不形成业务产品；至少采用两个不同的模拟任务领域，避免接口只服务于单一示例。独立示例工程、测试套件与测试数据属于内部工程资产，不公开交付；指南中的必要 API 用法片段属于文档，不提供独立示例项目或测试套件。

## 3. 必须保持的框架原则

### 3.1 机制与策略分离

- 内核负责受信任的权限、资源 admission、生命周期、规范事件和错误传播。
- 策略负责“给模型看什么”“下一步允许提出什么”“何时修正或询问用户”。
- 官方参考 Agent 是策略的一个实现，不是唯一执行方式；现有自定义 Agent 和无模型 Echo Agent 路径仍应成立。
- 策略不能通过修改 prompt、工具视图或返回值，绕过工具授权、预算、终态或会话结算。

### 3.2 抽象有明确的使用者和边界

- 公共接口不得依赖示例项目的业务名词、数据库表、模型型号或 HTTP 客户端类型。
- 新接口应由正式实现和独立测试实现共同验证；不为了证明抽象而新增第二套真实后端。
- 优先采用类型化值和范围受限的接口，避免任意字符串协议、全局上下文对象和万能 middleware。
- 不要求每个策略都成为新的 runtime/provider。策略可以通过 builder 或构造参数注入；crate 拆分由依赖关系决定。
- API 名称、trait 签名和 crate 新增数量不由本 PRD 冻结，在对应 ADR 中确定。

### 3.3 显式组合和安全默认值

- 不自动下载模型、启动推理服务、读取未声明的配置来源、访问云端或扩大工具权限。
- 已声明必需能力的唯一候选解析可保持现有行为；不得将可选能力静默激活。
- 能力不支持时返回明确错误；降级必须由宿主显式允许，并可观察。
- 官方端侧预设必须有有限步数、修正次数、总时长、输出和并发限制，实际数值通过基线实验确定并记录版本。
- 受信任宿主可覆盖预设，但模型生成内容和不受信任工具数据不得提高这些上限。

### 3.4 可靠性语义不得倒退

- SessionRuntime 继续拥有规范事件地址与会话内顺序；策略不能直接伪造终态。
- 回合最多提交一个规范终态；已有失败收尾、能力排空和显式 shutdown 语义继续有效。
- 丢弃等待句柄不等于取消；预算触发的停止也必须进入可审计的收尾流程。
- 审计日志、任务状态和模型上下文各自有清楚的来源与一致性边界。
- 持久事件去重、模型重试和外部工具幂等性是不同概念，不互相替代。

### 4.1 本版本非目标

- 通用多 Agent 调度、自动任务分派和跨进程分布式执行。
- 通用图编排 DSL、任意 Rust Future 快照或恢复正在运行的线程。
- 模型训练、微调、权重分发、量化实现或自研推理引擎。
- 自动模型路由、云端兜底、多模型同时驻留和 KV cache 调度算法。
- 强制向量数据库、完整长期记忆产品或默认 LLM 摘要服务。
- 动态插件 ABI、插件商店、完整 MCP 生态接入。
- 操作系统级沙箱产品，以及对任意外部操作的 exactly-once 保证。
- 业务 UI、聊天客户端、特定行业项目；原生 Android/iOS 部署认证。

## 5. 目标架构与职责

| 层 | 职责 | 禁止承担的职责 |
| --- | --- | --- |
| 核心契约 | 消息、动作、任务标识、预算、状态、事件和错误词汇 | 特定后端网络类型、业务工作流 |
| 受控 runtime | admission、授权、取消、排空、事件提交、状态访问边界 | 隐式制定任务计划或替应用认定业务完成 |
| 可替换策略与参考 Agent | 上下文选择、动作决定、修正、完成检查接口、局部步骤组织 | 绕过 runtime 调用原始工具或提高权限 |
| 适配器 | 模型协议映射、token 计数能力、工具与存储实现 | 向上泄漏服务端私有协议作为框架公共语义 |
| 宿主应用 | 业务目标、业务状态 schema、完成规则、路径、权限和配置 | 必须重写所有通用模型工具循环 |

建议沿现有 core / llm / tools / session / plugin / runtime / sdk 边界演进。参考 Agent、上下文策略和任务状态可放入独立可选 crate；是否拆分由 M1 的依赖图决定，不能先创建大量空抽象。

三个不同的身份必须明确：Session 用于事件与对话关联；Turn 用于一次运行及其规范收尾；Task 用于可跨 Turn、可恢复的工作。恢复默认开启新 Turn，不重新打开已经终止的 Turn。

## 6. 功能需求与验收

### F1：结构化模型与动作协议

#### 必须实现

- F1.1 定义后端中立的模型请求/结果：普通文本、assistant 工具调用、工具结果及关联 ID；消息角色与内容组合可验证。
- F1.2 定义类型化生成约束和能力描述，至少表达：普通文本、原生工具调用、结构化 JSON 输出、流式支持、结束原因及 token 计数/用量可用性。
- F1.3 支持两条显式路径：原生工具调用；受约束动作输出。默认动作最少包含 `CallTool`、`Final`、`AskUser`。这些是概念名，不是冻结的 Rust API。
- F1.4 约束动作输出只允许当前可见且已授权工具集合中的候选动作；执行前仍由 ToolRuntime 独立校验和授权。
- F1.5 同一动作必须关联到模型请求、执行步骤、工具调用与结果。provider 返回的 ID 不直接作为受信任的运行时身份或跨恢复幂等键。
- F1.6 结果必须表达正常完成、输出长度截断、工具调用、取消、失败或未知结束原因；缺失 usage 必须标为未知，不记作零。
- F1.7 升级现有本地 OpenAI-compatible 适配器；在能力确实支持时传递工具声明和结构化约束，处理完整响应和分片响应。
- F1.8 不执行未完整接收、未校验的流式工具参数；原生模式一次产生多个动作时按声明策略顺序处理或明确拒绝，不静默遗漏。
- F1.9 首版不要求暴露全部采样参数；必须记录影响评测的实际模型、量化、模板、服务端版本与采样配置。未知字段显式标注。
- F1.10 框架侧 schema 校验与后端生成约束分别声明支持范围；不能因为后端忽略部分 schema 关键字而宣称整个 schema 已被强制满足。

#### 验收

- AT-F1-01：假 provider 与本地真实 provider 通过同一组请求、动作、结果契约测试。
- AT-F1-02：非法 JSON、错误工具名、参数缺失、参数 schema 不满足时，工具执行次数为零。
- AT-F1-03：请求不支持的约束时，在首次推理前可判定的错误提前失败；无法提前确认时不得宣称已强制约束。
- AT-F1-04：覆盖中文 UTF-8 跨分片、SSE 跨分片、截断、缺少终止信息、取消和 usage 缺失。截断动作不按成功动作执行。
- AT-F1-05：保留纯文本模型和无模型 Agent 路径；两种动作模式均有内部可执行验证，公开指南提供必要用法片段与兼容性说明。

### F2：上下文构建与预算

#### 必须实现

- F2.1 将审计事件、任务状态和模型上下文分离。上下文构建是有输入、有输出、可测试的策略，不修改历史日志。
- F2.2 提供默认对话投影：用户消息、完整 assistant 回复、工具调用和工具结果正确关联；流式 delta 不与完整回复重复拼入。
- F2.3 明确完整 assistant 回复的规范持久化位置与写入顺序。Agent 仅返回 `final_text`、不 emit delta 时，也能在之后的会话中恢复完整回复；写入失败不得被静默当作成功。
- F2.4 上下文预算覆盖 system 指令、消息、工具 schema、模板开销、预留输出和安全余量。硬预算要求可信计数或可验证上界；仅有启发式估算时必须标为软预算或拒绝硬预算模式。
- F2.5 默认裁剪保护当前请求、必要约束和未完成的调用/结果组。最低必要上下文都无法放入时，明确失败，不静默丢弃权限或用户约束。
- F2.6 工具可见性策略只能在授权集合内选取子集；提供确定性的分组/筛选默认实现，保留应用自定义选择接口。
- F2.7 支持工具结果到模型视图的精简转换；大结果可分页或以受控内容引用按需读取。引用的作用域、存储位置、大小和有效期由宿主声明，不自动暴露任意文件路径。
- F2.8 保存上下文构建报告：来源事件/状态版本、保留与剔除项、计数方法和预算。模型摘要属于派生信息，不能无依据覆盖规范事实。
- F2.9 工具输出和检索内容保持不受信任数据身份，不因进入摘要或任务状态而提升为 system 指令。

#### 验收

- AT-F2-01：同一事件/状态快照和确定性配置产生相同的上下文与构建报告。
- AT-F2-02：只返回 `final_text`、流式回复、工具往返、版本化历史四组回归用例通过；缺失字段明确标记未知，不捏造补全。不要求读取旧的无版本模型负载。
- AT-F2-03：长历史、长工具输出和工具 schema 增长时，精确计数模式不超过预算；软计数模式有可见标签和保守失败行为。
- AT-F2-04：替换上下文策略不修改 AgentRuntime、SessionRuntime 或模型适配器；上下文压缩不改写审计文件。
- AT-F2-05：未获授权的工具不能通过自定义选择策略出现并被执行；提示注入测试验证工具数据不能扩大权限。

### F3：有限参考 Agent

#### 必须实现

- F3.1 提供可选官方 Agent 实现，组合模型、上下文、动作解释、修正和完成检查策略。普通自定义 Agent 不依赖这一实现。
- F3.2 基本循环为：读取状态 → 构造上下文 → 请求下一动作 → 校验 → 执行/回答/询问 → 写入受控结果与状态 → 判断是否继续。
- F3.3 默认每一步只推进一个已验证动作；框架内部确定性操作不强制调用模型，也不要求模型输出完整计划或私有推理过程。
- F3.4 对格式和参数错误提供短而结构化的反馈，限制修正次数；权限拒绝、用户拒绝和非幂等执行不确定性不得通过普通修正自动绕过。
- F3.5 支持 `AskUser`：产生可持久化的待答状态并正常结束当前 Turn；宿主携带答复显式开启后续 Turn，不无限占用等待任务。
- F3.6 提供无进展检测接口和默认实现：结合相同动作、参数、反馈与状态版本识别重复；支持合法轮询的宿主声明，不把所有重复调用一概判为错误。
- F3.7 定义完成检查接口。模型声明完成与业务条件已验证必须在结果/证据中区分；通用框架不能替应用发明业务成功条件。
- F3.8 终止原因至少区分完成、等待用户、无进展、预算耗尽、取消和不可恢复错误，并保持现有终态/结算的一致性。
- F3.9 策略函数不得获得能绕过授权的原始工具、能任意写事件信封的对象或任意提升预算的权限。

#### 验收

- AT-F3-01：无工具回答、单工具、多步依赖、错误修正和缺参数询问五条路径可通过公共 API 运行。
- AT-F3-02：持续生成非法动作、持续重复调用或持续声称完成但校验失败时，在配置上限内停止。
- AT-F3-03：内部完整示例证明应用无需编写通用 while/tool loop；另一个内部示例可完全替换 Agent 实现且继续使用相同 runtime。
- AT-F3-04：用户拒绝后不能换工具绕过；所有停止路径都保留原因、已接受工作的收尾结果和可查询证据。

### F4：任务级资源控制

#### 必须实现

- F4.1 提供类型化预算：步骤数、模型请求数、工具调用数、修正次数、总执行时长、输入/输出 token 预算，以及工具结果大小。
- F4.2 区分宿主上限、任务累计额度、单 Turn 和单调用额度；取更严格限制。Task 恢复和 `AskUser` 后继续不能重置累计调用额度。
- F4.3 模型调用增加最大并发、有限等待队列、取消排队和过载错误；排队阶段必须计入运行截止时间。默认调度无需实现设备驱动层资源管理。
- F4.4 并发 admission 原子预留预算，避免同时检查通过后超额；修正、摘要等框架发起的模型请求也必须经过同一计量路径。
- F4.5 用量区分实际值、预留值、估计值和未知值；无法取得精确 usage 时不得通过记零让循环无限继续。
- F4.6 预算耗尽后禁止接收新的动作，并协调取消/排空。工具执行超时不承诺撤销已经发生的外部副作用。
- F4.7 区分执行截止时间和清理阶段。清理未完成时明确报告，不通过丢弃 future 伪装为完成；不承诺强制停止进程内任意阻塞代码。
- F4.8 提供运行报告：等待时间、模型耗时、工具耗时、请求/修正次数、token 用量可信度和停止原因。时间度量来源可替换以支持确定性测试。
- F4.9 默认总执行时长累计各次运行的活动时长，包含 admission 排队，不包含已持久化的等待用户时间；单次运行采用单调时钟，任务跨重启保存累计消耗。宿主如需包括等待用户在内的绝对期限，应另设任务到期时间。

#### 验收

- AT-F4-01：并发压力测试中，已接受模型调用数不超过并发上限，队列长度不超过配置，预算计数不因并发而透支。
- AT-F4-02：模型一直返回继续动作、没有 usage、调用者取消、排队超时四种情况均有有限且可解释的退出行为。
- AT-F4-03：自定义 Agent、官方参考 Agent 和修正策略的所有受控模型/工具调用受相同预算约束。
- AT-F4-04：任务恢复后保留已消费额度；宿主显式追加额度有审计记录，模型不能自行追加。

### F5：内部示例、测试与真实小模型评测

#### 必须实现

- F5.1 内部维护无需模型和网络的 smoke 示例，以及使用宿主已启动的本地模型的入门示例；示例不自动下载模型，不随公共源码或 Cargo 包交付。
- F5.2 提供至少两个不同领域的可执行模拟场景，使用公开 API 和替换式工具实现，不引入业务数据库/界面依赖。
- F5.3 在内部验证工程建立 fake provider、假时钟、假工具和故障注入存储；支持记录与测试重放。重放模式不会真实执行外部副作用，并与生产恢复区分；不为公开框架引入这些测试依赖。
- F5.4 固定至少 40 个不同任务用例，覆盖多步依赖、缺信息、无可用工具、非法参数、重复动作、长上下文、长结果、取消、预算、恢复及副作用不确定性。
- F5.5 至少两个不同的小参数模型，各固定一组权重/量化/模板/采样配置；在一台确认的设备上执行同一验收集，每个配置至少三次运行。
- F5.6 报告任务实际状态正确率、非法/越权动作拦截、无效循环、修正次数、累计 token、端到端延迟和峰值内存。推理服务与宿主内存分别记录；不可测量项明确标注，能耗是可选指标。
- F5.7 用相同模型配置、任务和工具权限做基线及消融：比较基础有限循环与上下文策略、结构化约束、修正策略的独立影响。不能预先宣称提升或事后删除失败任务。
- F5.8 第一批真实基线结果必须完整留存供内部验收；待基线建立后，在 M3 前冻结 RC 的逐配置质量和性能门槛。没有冻结门槛或没有达标，不得宣布 v0.1 质量验收通过。公开指南可说明已验证的支持范围和限制，但原始报告、任务集及重放数据不自动公开。

#### 验收

- AT-F5-01：所有确定性契约/故障测试通过；至少 40 个任务全部执行，不存在以“模型失败”为由漏记的样本。
- AT-F5-02：安全测试中未授权副作用执行数为零；恢复测试中未批准的重复非幂等执行数为零。此项是测试集门槛，不是对任意场景的绝对安全保证。
- AT-F5-03：内部报告包含权重版本、量化、模型模板、后端版本、设备、并发、采样参数、运行次数、原始失败分类和复现命令；结果不能只提供总分。
- AT-F5-04：指定设备上的两组真实模型报告完成内部验收，并满足已冻结的质量/性能门槛；异常波动有记录，不只选最好一次。
- AT-F5-05：从公共交付源码或打包结果进行隔离构建，与内部测试结果对应；验收资料有可恢复的私有保存方式。检查公共 Git 清单、Cargo 包清单及源码内嵌测试，确认没有泄漏内部示例/测试资产。

### F6：任务状态、检查点与安全恢复

#### 必须实现

- F6.1 提供 Task 身份和版本化状态契约。框架管理状态版本、事件游标、执行步骤和累计预算；业务 payload 的 schema 与解释权属于应用，默认 Agent 仅使用自己的命名空间。
- F6.2 提供可替换存储接口和一个官方本地持久实现；支持按预期版本更新，冲突时明确失败。不得把 Tokio future、线程或 provider 客户端写入状态。
- F6.3 定义日志与检查点的一致性协议：检查点只引用已确认持久的事件和已结算动作；派生快照可从规范事件重建，不引入未说明的双写原子性假设。
- F6.4 安全检查点至少包括已完成步骤边界和等待用户状态。重启后由宿主显式恢复，开启新 Turn，并校验 Agent/策略版本、工具集合及状态 schema。
- F6.5 恢复不自动重放历史模型请求或历史工具调用。发现日志中动作已发出但结果缺失时，进入待核验状态，不把“没有结果”解释为“没有执行”。
- F6.6 工具可声明只读、可幂等重试或非幂等副作用；运行时为可重试逻辑动作管理跨尝试稳定的幂等键，具体工具负责真正兑现幂等性。
- F6.7 非幂等或幂等能力未知的工具，在执行结果不确定时默认停止，允许宿主通过结果核验/用户确认继续；不允许自动补发写操作。
- F6.8 恢复重新检查当前权限；旧审批或旧授权不能自动适用于新的动作或变化后的参数。
- F6.9 v0.1 不支持多个进程同时写入同一 JSONL 根目录；必须在指南中说明，并检测/拒绝可检测的冲突。存储替换接口不等于已实现跨进程协调。

#### 最小恢复状态表

| 重启时可证明的状态 | 恢复行为 |
| --- | --- |
| 尚无已持久化的动作意图 | 从此前安全边界重新决策；工具不得在动作意图持久化前开始产生副作用 |
| 动作意图存在，但没有持久结果 | 标为执行结果不确定；只读/已声明幂等工具按明确策略核验或重试，其他工具等待宿主核验 |
| 动作结果已持久化，但状态快照尚未更新 | 从规范事件重建状态；不再次执行已确认的动作 |
| 安全检查点及其关联事件完整 | 校验版本、权限和预算后，从后续步骤开启新 Turn |
| 已持久化等待用户 | 返回待答状态；仅在宿主提交关联答复后继续 |
| 日志损坏、快照引用未确认事件或版本不兼容 | 明确拒绝恢复，保留诊断信息，不自动清空日志或另起同名任务 |

#### 验收

- AT-F6-01：在模型返回后、工具调用记录后、工具产生副作用后、结果记录后和检查点提交时注入终止，重启行为均符合状态表。
- AT-F6-02：已确认完成的步骤不重复执行；未确认的非幂等步骤进入待核验状态。
- AT-F6-03：使用可幂等测试工具时，同一逻辑动作多次尝试仍只有一次可见副作用；不能据此声称普通工具也具备 exactly-once。
- AT-F6-04：`AskUser` 后重启、提交答复、继续执行可跑通，并保留权限和累计预算限制。
- AT-F6-05：状态版本冲突、未知 schema、策略版本不兼容和损坏日志均产生明确错误，不静默清空状态重新开始。

## 8. 非功能需求与兼容性

### 8.1 离线、隐私与权限

- 已准备好依赖和模型的运行路径不依赖公网；不隐式读取密钥、不自动上传 telemetry 或评测数据。
- 网络范围、日志路径和持久化策略由宿主配置。示例写操作仅操作明确的临时测试目录。
- 区分规范审计内容与展示/导出内容：默认 Debug、诊断与报告不得输出凭据；日志可能包含敏感业务内容，必须明确告知。
- 提供受控的报告脱敏/裁剪路径；不得对完整事件先任意脱敏再声称仍可精确重放。删减内容后的重放能力必须有标记。
- 进程内工具和插件属于受信任宿主代码，不承诺隔离恶意实现；对不受信任代码应通过外部执行器扩展，而非靠 prompt 防护。

### 8.2 性能与资源

- 评测区分 harness 自身开销和模型推理开销，不预先给出无基线支撑的毫秒、token/s 或内存承诺。
- 检查长日志和长会话增长路径；当前 JSONL 每次追加读取历史、会话 admission 克隆历史的成本需进入压力基线。
- 若索引/缓存优化必要，必须保持日志物理顺序、去重、提交确定性和恢复语义；不得为提速静默移除持久化屏障。
- 默认并发与队列有界；超出支持的内存/上下文规模时明确拒绝或进入文档化降级，不无限增长。

### 8.3 API、事件和版本

- 未上线阶段不保留旧文本 API 或兼容别名，直接采用 generate/generate_stream。文本功能、取消、超时、规范记录与收尾必须有回归；Echo Agent、自定义 Agent 和 provider 装配的非模型接口不作无关改动。
- 在 M1 冻结消息、事件、Task 状态和错误版本策略；新模型记录显式 version: 1，无版本和未知版本拒绝。不提供旧模型日志自动读取/迁移，宿主需要旧数据时先备份再作显式决定。
- 不重写旧日志来伪装缺失的 assistant 内容、usage 或完成证据。旧版缺失信息必须保留“未知”语义。
- 各 Jingwei crate 一起发布到一致版本/提交；包版本、Rust 工具链和 MSRV 声明必须通过真实验证，不仅沿用 manifest 数字。
- 工具链固定为 Rust 1.96.0，workspace 的 rust-version 已从不准确的 1.85 修正为经过本机验证的 1.96；跨平台及持续最低版本验证仍需完成。

### 里程碑顺序

实施调整（2026-09-03）：用户要求尽快进入开发。构建基线、工具链下限和私有测试目录边界已足以支持无 IO 的契约开发，故 JW-01/JW-02 已开始；模型选型、异机备份和完整指南站继续跟踪，不再阻塞这批纯协议实现，但仍须在对应验收/发布门槛前完成。首批进度详见内部记录 docs/internal/implementation/JW-02-a.md，不能将其视为 JW-01/JW-02 或 F1 全部验收。

- M0：范围与基线。完成 JW-00，并启动 JW-09；确认本 PRD 后才开始实质实现。
- M1：框架契约。完成 JW-01 和 JW-02 的骨架/契约测试；恢复语义在此阶段设计，而非最后补救。
- M2：受控模型入口。完成 JW-03、JW-04；同时构建测试驱动和第一批真实基线。
- M3：小模型执行闭环。完成 JW-05、JW-06；进入阶段前冻结真实评测的 RC 门槛和支持配置。
- M4：跨重启可靠性。完成 JW-07，贯通故障测试和恢复教程。
- M5：版本交付。完成公共源码/开发指南、内部示例/报告验收和 JW-10；单独核验 Cargo 包边界，线上发布另按权限执行。

不预估日历工期；每个里程碑结束后根据实测、接口稳定性与文档消费测试调整下一阶段工作量，不默默扩大功能范围。

## 12. PRD 的实施使用方式

1. 先确认版本范围和第 3 节框架原则，再执行 JW-00。
2. 每次选一个 JW 任务进入技术设计；技术设计引用 F/AT 编号，并补充具体测试与迁移方案。
3. 涉及公共契约或持久格式的变更先形成 ADR；PRD 中的概念名不能直接当作已批准 API。
4. 完成后同步更新实现、测试、指南和本清单；未达标项保留，不以“代码已合入”替代验收。
5. 如果实测否定某个默认策略，应替换策略并保留框架契约，而不是为示例临时硬编码模型行为。

v0.1 的完成标志是：开发者可以依据公开指南，用公共接口组合出受控的小模型 Agent，并验证其预算、安全退出和恢复边界；不是仅增加一组接口或完成一个演示项目。
